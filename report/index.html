DuckDB-Wasm 三个方向的实验结果

实测环境：Apple M3 Ultra（32 核）/ 256 GiB / macOS 26.6 / Node 24.18 / Chromium 145 / DuckDB 2.0.0 (native) · duckdb-wasm 1.33.1-dev118（内嵌 DuckDB 1.5.4）· 2026-11-19

三句话结论
  • 分片并行把单线程的短板基本补上了：16 个 wasm 实例在 SF1 上把 Q1 从 251ms 压到 24ms（10.3×）， 追到原生 32 线程（14ms）的 1.7× 以内，但没有反超。
  • 本地优先运行时成立：OPFS + 跨标签页单写者 + 迁移 + 导出全部实测通过（10/10）， 导出的 .duckdb 能被原生 CLI 直接打开。
  • 三引擎同页对比：200 万行下 DuckDB 聚合比 SQLite 快约 15×、比 PGlite 快约 24×， 而三家结果一致到 1e-14。

1. 分片并行：把“单线程”这个天花板绕过去

duckdb-wasm 默认 bundle 是编译成单线程的，SET threads=4 会直接报 DuckDB was compiled without threads。但“单实例单线程”不等于“只能用一核”： 可以起 N 个独立实例，每个扫一部分分片，各自算部分聚合，主线程只合并几十行结果。

wasm 单实例比原生单线程慢约 1.5×（251 vs 168ms）——这是 wasm 的真实单核开销。 16 个 wasm 实例把差距压到 1.7×（24 vs 14ms），但没有反超：原生多线程共享一份已解压的 column chunk 缓存，而 16 个实例各自读各自的 parquet 分片，压缩数据被重复解压、页缓存也不共享。 早年我若拿"wasm 热态"去比"原生冷态（含进程启动）"会得出反超的错误结论；把两边都放到同一进程里 跑热态后，原生仍然领先。代价还包括内存：每个实例一份 wasm 堆（本例约 120 MB/实例）。

SF10 上 16 worker 达到 16.1×，接近线性；Q6 在 16 worker 时略低于线性（14.1×）， 因为它的总耗时已经压到 65ms，worker 启动与结果合并占比变大。注意 SF10 的 16 worker（151ms） 仍然慢于原生 32 线程（SF10 热态实测 90ms，四次中位），并行层的作用是"把单线程的 16 倍差距缩到 1.7 倍"， 而不是"比原生快"。

什么时候不该用这招：单次查询少于 ~50ms、或者数据本来就小（<100 万行）时， 16 个实例的 2.8s 池初始化成本永远收不回来。它适合“长驻会话 + 大表反复查”， 不适合“打开页面查一次就走”。

2. 本地优先运行时：OPFS + 跨标签页

duckdb-wasm 的 OPFS 只解决“文件能持久化”。真做本地优先应用还要解决： 两个标签页同时打开同一个库怎么办、schema 怎么演进、浏览器随时被杀时数据怎么不丢、 用户怎么把数据带走。这一层目前没有现成库。

踩到的三个真实坑（文档没写）

  • OPFS 路径不是根目录：1.33 把库放在 duckdb/fs/<name>， 临时文件在 duckdb/scratch/。按文档的思路从根目录找文件会 NotFound。
  • DuckDB 没有 PRAGMA user_version：SQLite 的迁移惯例在这里不成立， 要自己建元数据表。
  • 锁回调不能 await：navigator.locks.request() 的 promise 在锁释放前不 resolve， 在回调里 await 一个“保持到 destroy”的 promise 会把 start() 直接挂死。必须先 resolve 一个就绪信号， 再单独挂起。

3. 三引擎同页对比（DuckDB / SQLite / PGlite）

同一个标签页、同一份 CSV（TPC-H lineitem 20 万行，按 repeat 参数放大）、同一套 SQL 语义。 方言差异显式处理：DuckDB 和 Postgres 支持 DATE '1994-01-01' 字面量，SQLite 不支持， 只能存 ISO 文本做字符串比较。

为什么是这个数量级：DuckDB 是列存 + 向量化执行 + 直接读 Parquet/CSV 的零拷贝路径； SQLite 是行存 B-tree，聚合要逐行解码；PGlite 走 Postgres 的堆表 + wasm3 解释执行， 每次查询还有协议层开销。三家的 Q6 结果一致到 1e-14，说明差的是执行方式，不是正确性。

别误读这张表：SQLite 在这三个引擎里导入最慢（15.4s），但它的价值是事务、并发、 小对象读写和 30 年生态，不是 OLAP 聚合。拿它跑分析查询本来就不是它的战场； 反过来，DuckDB 也不适合高频单行 UPDATE。

4. 跨机器访问：为什么 http 不行

把服务绑到 0.0.0.0 只解决“能不能连上”。真正卡住的是浏览器的安全上下文： OPFS、Web Locks、SharedArrayBuffer 只在 secure context 暴露，而 http://localhost 算 secure context，http://10.10.10.81 不算。

实测脚本 test/lan-probe.mjs / test/lan-probe-tls.mjs。 https 下 crossOriginIsolated=true（COOP/COEP 生效），本地优先运行时在远端机器上 完整可用：leader 选举、500 行写入、第二个标签页读、关闭后接管，全部通过。 代价是自签证书警告（另一台机器点一次继续），或用 mkcert 签本机 CA。

5. 结论与建议

  • 要做分析型产品：DuckDB-Wasm 是唯一正确选择，尤其数据在 Parquet/CSV/对象存储上。
  • 数据 > 500 万行且反复查：上分片并行层，16 worker 在本机是甜点（内存换速度）。
  • 要"打开即用、下次还在"：必须自己做运行时（OPFS + 锁 + 迁移 + 导出）， 直接用 duckdb-wasm 会在多标签页和升级路径上踩坑。
  • 需要事务/高并发小写入：SQLite-Wasm 或 PGlite 更合适，别硬用 DuckDB。
  • 版本：npm i @duckdb/duckdb-wasm 会拿到 OPFS 坏的 dev57， 必须钉 1.32.0 或 @next（≥ dev61）。

复现：./scripts/make-data.sh 重建数据 → node bench/scale.mjs / node test/run-compare.mjs / node test/run-warehouse.mjs（后两者需先 node test/server.mjs）。 所有数字均由本机实测脚本产出，未引用二手来源；parquet 数据不进仓库，脚本可重建。
